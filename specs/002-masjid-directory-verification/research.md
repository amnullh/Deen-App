# Research and Decisions: Phase 1 (Masjid directory, verification, schedules)

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-10-22

Every version, license and price below was checked on a live source on 2026-10-22 (npm registry, PyPI, GitHub, vendor pages) unless marked **UNVERIFIED**. Where two research reports disagreed, the decision below says which one won and why. "Owner decision" items are collected in plan.md.

Conventions: each entry is **Decision / Rationale / Alternatives**. Licenses follow constitution principle 10: OSI open source, free with no paid tier, permissive for anything shipped to a phone or a browser, copyleft only for separately run server-side processes.

## 1. Architecture

### R-01 Static-first read path, three hostnames
- **Decision**: Listeners only ever read static files. A build job writes the manifest, region packs and per-cell schedule layers to disk; Caddy serves them. No listener request reaches the API or the database. Three hostnames: `data.<domain>` (static, cookieless, no access log), `api.<domain>` (public listener writes only: suggestions and abuse reports; no cookies; the only host the app ever POSTs to), `console.<domain>` (the operator console as static files plus the admin and Operator API under `/v1/*` on the same origin; `/v1/public/*` exists only on `api.<domain>`).
- **Rationale**: The same origin for console and admin API allows a `__Host-` session cookie, `connect-src 'self'`, no CORS and simple CSRF defence (R2, R1). A separate cookieless `data.` host lets its logging be switched off without touching admin logging (FR-027). Keeping listener writes on their own host means admin routes are unreachable from the public internet path the app uses.
- **Alternatives**: one host for everything (rejected: mixes logging policies); separate API origin with CORS and credentials (rejected: weaker cookie, more headers, more attack surface); a CDN (rejected: freemium SaaS, principle 10).

### R-02 Repository layout
- **Decision**: Keep the owner's layout. `services/api` (Fastify API and worker, one image, two entrypoints), `services/domain` (shared TypeScript: claim transition table, authorization policy table, generated API types), `apps/operator-console` (Vite SPA), `infra/` (compose, Caddy, bootstrap, runbooks), `packages/masjid_schedule` (pure Dart, new), `packages/directory_client` (Dart, new, the only network code in the app). One `pnpm-workspace.yaml` at the repository root lists `services/*` and `apps/operator-console` only. The OpenAPI file stays at `specs/002-masjid-directory-verification/contracts/openapi.yaml` and is the single source for server routes, generated types and tests (tasks copy nothing; code reads it by path).
- **Rationale**: The root `pubspec.yaml` names its Dart members explicitly, so pub never sees the Node workspace and no name clashes occur. CI path filters keep Phase 0 jobs fast (R7).
- **Alternatives**: R2 proposed a self-contained `server/` directory. It is cleaner but departs from the owner's stated layout; the clash it avoids does not exist because pub reads an explicit member list.

### R-03 Runtime and tooling
- **Decision**: Node.js 26 (becomes LTS on 2026-10-28; `engines >=24`; CI also runs 24), TypeScript 6.0.3 for type checking only (`tsc --noEmit`), run with Node's native type stripping, so there is no build step and no `tsx`. pnpm 12.14 (pnpm 11+ blocks install scripts by default and has a release-age gate; npm hard-fails peer resolution on TypeScript 6 with `openapi-typescript`).
- **Rationale**: Fewest moving parts (principle 9). TypeScript 7 has no stable programmatic API until 7.1 and typescript-eslint pins `<6.1`.
- **Alternatives**: Node 24 (maintenance since 2026-10-20), tsx, tsdown, npm workspaces.
- **Rule**: only erasable TypeScript syntax (no enums, decorators or parameter properties); `verbatimModuleSyntax`; `.ts` import extensions.

### R-04 HTTP framework, database access, job runner
- **Decision**: Fastify 5 (MIT) over NestJS (MIT): about 15 MB less RSS, 76 vs 105 transitive packages in a like-for-like measure, and NestJS decorators would force a build step. Kysely 0.29 + `pg` (MIT) over Drizzle: the domain is SQL-heavy (triggers, PostGIS, `REVOKE`, partial indexes), Kysely keeps the schema SQL-first with generated types and has no runtime dependencies. Migrations are plain forward-only `NNNN_name.sql` files applied by Kysely's migrator. pg-boss 12 (MIT, needs PostgreSQL 13 or later) runs jobs in PostgreSQL itself.
- **Rationale**: All measured by R2 (idle RSS 89 MB for the API with plugins). Drizzle is Apache-2.0, not MIT as the brief said, and has 2,000 open issues with the 1.0 line still in release candidates.
- **pg-boss risk**: one maintainer. Mitigation: every timer is a database column and every job is an idempotent sweeper, so replacing it with Graphile Worker (MIT) or `pg_cron` is a small port.
- **Alternatives**: NestJS, Hono, Drizzle (+drizzle-kit), BullMQ (needs Valkey as a queue: rejected), systemd timers.

### R-05 Valkey is kept for sessions, replay protection and rate limits
- **Decision**: Run Valkey (BSD-3-Clause) for admin sessions, TOTP single-use markers and rate-limit counters. A `sessionEpoch` column in PostgreSQL is bumped on every credential change, so a stale Valkey snapshot can never revive a revoked session.
- **Rationale**: The owner listed it, the constitution's Technology Constraints list it, it costs 15 to 64 MB, and it keeps hot per-request counters off PostgreSQL. R2 and R3 observed that PostgreSQL could do the job; that stays a documented fallback behind the same interfaces. Recorded in Complexity Tracking.
- **Alternatives**: PostgreSQL-only sessions and counters; in-process memory (loses state at restart).

### R-06 Schedule rule expansion: one Dart implementation compiled to JavaScript
- **Decision**: Rules are the published artifact. A new pure-Dart package `packages/masjid_schedule` owns the rule model, validation and day expansion, reusing `prayer_engine` for calculated times. It is used (a) in the app (authoritative), (b) in Node by the API, for validation on save, and (c) in the console, in a Web Worker, for the 14-day preview. The JavaScript comes from `dart compile js -O2` in CI.
- **Evidence** (R6 spike): the compiled `prayer_engine` ran identically in Node and in the Dart VM on 13,664 day rows (8 cities including a polar city and the date line, 14 methods, 122 days, every instant compared in milliseconds: zero differences). Bundle 1.5 MB, 100 KB with brotli; most of it is the `timezone` database, which can shrink with the 10-year data set.
- **Why not a TypeScript port**: Phase 0's engine has three custom corrections over `adhan_dart` and a 1-minute accuracy bar; a port needs the same oracle work again and any drift between the console preview and the phone would break admin trust (FR-020). Shared vectors detect drift but do not prevent it.
- **Deviation from the owner's outline**: the brief says the generator expands rules into dated times for 30 days. The server publishes the rules only (no pre-expanded `x` rows, which R4 suggested) and the phone expands them: calculated-plus-offset times need Masjid coordinates and the device's engine and OS time zone data, so only the phone can be authoritative, and one expansion path means no second source of truth. The server runs the same compiled code only to validate on save and to build golden vectors. The phone's 30-day horizon is `syncedAt + 30 days`.
- **Time zone data**: the phone prefers its own OS offsets for its own zone and uses the bundled `timezone` data (tzdata 2026e) for other zones. After a government rule change the console preview (bundled data only) can differ from a phone until the app updates; the console footer shows the tzdata version.
- **Risks and mitigations**: a Dart SDK is needed in server CI (already pinned for Phase 0: free). dart2js output is tied to the pinned SDK. Golden expansion vectors (`packages/masjid_schedule/test_vectors/*.json`) are generated by the Dart expander and replayed by `dart test` and `node --test`, so a future TypeScript port stays possible.
- **Alternatives**: TypeScript re-implementation (A), device-only (C), `dart compile exe` sidecar called from Node (no browser preview).

### R-07 The app's network: one choke point, signed data
- **Decision**: A new package `packages/directory_client` owns all HTTP in the app. It uses `dart:io` `HttpClient` directly (no new pub dependency). It exposes typed calls only: manifest, country summary, cell parts, schedule layer, and two POSTs (suggestion, abuse report). `EgressPolicy.check(Uri)` runs before every request and on every redirect: HTTPS only, the configured host only, no query string, no userinfo, a path regex allow-list, a fixed header set (`Accept`, `Accept-Encoding`, `If-None-Match`, a constant `User-Agent: DeenDirectory/1`), no cookies, no authorization. It needs a persisted consent object and a build-time base URL; an empty base URL gives a null client that opens no sockets (the Phase 0 kill switch). Android adds `INTERNET` only, `usesCleartextTraffic=false` and a network security config; `ACCESS_NETWORK_STATE` stays forbidden.
- **Rationale**: Phase 0 enforces "no network" only by manifest, plist, a denylist and CI (R6). Phase 1 changes that to an auditable single choke point and an import-boundary scan.
- **What changes in Phase 0 tooling**: `tools/license_scan/bin/check_network.dart` gains INTERNET-allowed-with-conditions, an import-boundary scan (network symbols only under `packages/directory_client/lib`; `prayer_engine`, `schedule_planner` and `masjid_schedule` must not import `dart:io`), a URL-literal scan and `network_allowlist.yaml`.
- **Data integrity**: TLS plus a per-cell content hash (`cv`) and strict validation of every file before it is stored. Signed data files (Ed25519 over files, a key held off the server) were considered and are NOT in Phase 1: there is no CDN in the path, the build job needs the database and so would hold the signing key on the same server, and a library license check is still open. Signing becomes a Phase 2 prerequisite, before broadcast rights exist (plan.md, "Deferred to Phase 2").
- **Store consequence**: a region request sends the phone's IP address and a 5 km cell. Play Data safety and the App Store privacy label must be re-answered from the live wording; the honest default is "approximate location and IP, app functionality, not linked, not used for tracking" unless the stores' "processed in real time and not retained" exemption applies, which holds only if the server keeps no IP-bearing logs (FR-027 tightened in section 5 of the plan).

## 2. Authentication, sessions and email

### R-08 Authentication: in-house on Fastify
- **Decision**: In-house, ASVS 5.0 Level 2, built only from vetted libraries (no hand-written crypto). `@node-rs/argon2` 2.2.2 (MIT, Rust prebuilds, no node-gyp) for Argon2id; `otpauth` 9.5.2 (MIT) for TOTP; `@fastify/session`, `@fastify/cookie`, `@fastify/csrf-protection`, `@fastify/helmet`, `@fastify/rate-limit` (all MIT) with `ioredis` 6 (MIT) against Valkey. `node:crypto` AES-256-GCM encrypts TOTP secrets at rest.
- **Rationale**: Every custom flow the spec needs (Operator-approved second-factor reset, the break-glass with a call, a second Operator and a 48-hour delay, three Operator roles, step-up) must be written anyway. Keycloak needs 750 MB minimum (2 GB recommended): out on RAM. Kratos is a close second, but by default it fails ASVS 6.5.1 (TOTP reuse), likely 6.5.2 (recovery codes hashed), and 6.4.3 (recovery bypasses the second factor), has no built-in throttling, adds a process, a second data store and a UI for every flow, and had no release in the last seven months.
- **What would change this**: no reviewer with security experience available (then Kratos with `required_aal: highest_available`); listener accounts, passkeys or social login arriving (a real identity provider earns its RAM). An external review of the auth module is an exit criterion before Phase 2.
- **Alternatives**: Ory Kratos 26.2 (Apache-2.0), Keycloak 26.8 (Apache-2.0), `argon2` (node-argon2, MIT; equal but needs node-gyp).

### R-09 Credential policy and session model (summary; full rules in data-model.md and contracts/state-machines.md)
- Password: minimum 12 characters (Operators 15), maximum 128, any Unicode, no composition rules, paste allowed. Common and breached passwords blocked from a local list (the top one million from the MIT-licensed SecLists as a sorted SHA-1 file searched by binary search, zero RAM) plus context words. The full Pwned Passwords corpus (about 30 GB, licence not stated) and the k-anonymity API (external service) are rejected. A strength meter (zxcvbn-ts, MIT) runs in the browser only.
- Argon2id: 64 MiB, 3 passes, 1 lane, tuned on the real server to 250 to 400 ms; at most two hashes in parallel (`UV_THREADPOOL_SIZE=2`).
- TOTP: SHA-1, six digits, 30 seconds (the only combination every authenticator app accepts), window zero, single use per time step (`SET NX EX 90` in Valkey plus the last used step in PostgreSQL), secret encrypted at rest.
- Recovery codes: ten, 80 bits each, hashed with Argon2id, single use.
- Sessions: opaque 256-bit ids, stateful in Valkey (before the second factor is complete a separate 5-minute single-purpose `__Host-pa` cookie carries the pre-auth state and is never a session; pre-auth routes rely on the Origin check and JSON-only bodies), `__Host-sid` cookie (`Secure; HttpOnly; SameSite=Strict`), new id on login, step-up and role change. Timeouts: Muazzin and Admin idle 30 min and absolute 12 h; reviewer and moderator 15 min and 8 h; super-admin 10 min and 4 h. Concurrent sessions: 5 for admins, 2 for Operators. Step-up (password plus a fresh TOTP within 5 or 10 minutes) for claim decisions, suspend or revoke, ownership transfer, evidence viewing, role change, second-factor reset approval, break-glass steps, credential change and account deletion.
- Brute force: 5 failures per 15 minutes per account, 20 per 15 minutes per address, doubling cool-off to 24 hours; Operators lock after 10 until another super-admin unlocks; identical responses for unknown and known accounts (a dummy hash runs for unknown email).
- Password reset never bypasses the second factor (ASVS 6.4.3); reset tokens last 10 minutes and are single use.

### R-10 Email delivery
- **Decision**: Primary: Postfix with OpenDKIM on the host (outbound only; SPF, DKIM, DMARC; PTR matching; the API talks plain SMTP to `127.0.0.1:587` through `nodemailer` 10.2 (MIT-0)). Fallback, used only if the deliverability test fails or the provider keeps port 25 closed: a free relay (Resend free plan, Brevo as alternate) behind the same `SMTP_URL`, with a pre-written Exceptions Register row (plan.md, "Constitution actions").
- **Rationale**: Boring and proven (principle 9). R1 preferred Mox (one Go binary, MIT) but it is pre-1.0 (v0.0.17), has a single maintainer and had a 16-month release gap. R3 estimated Postfix and OpenDKIM at about 30 MB. Mox stays the alternative if Postfix wiring proves painful.
- **Hard facts**: Hetzner blocks outbound ports 25 and 465 by default and unblocks only after the account is a month old and has a paid invoice. Netcup blocks 25 by default with a self-service rule. OVH documentation conflicts. Contabo's policy is UNVERIFIED. A day-0 test (`telnet gmail-smtp-in.l.google.com 25` and reverse DNS control) is therefore a provider purchase gate.
- **Exit test** (14 days in the pilot): 40 messages (10 each to Gmail, Outlook.com, Yahoo and iCloud seed inboxes over 7 days): 100% `spf=pass dkim=pass dmarc=pass`; at least 95% in the inbox; zero hard bounces to valid addresses; reset email P95 under 60 seconds; the sending address on none of the major blocklists; TLS on at least 99%. Failing any item after one remediation round switches to the relay.
- **Volume**: under 20 per day for the pilot; about 400 to 700 per month at 500 Masjids; fits every free relay if renewals are queued at 60 per day.
- **Not used**: `smtp-connection` (EUPL-1.1), Amazon SES (paid), MTA-STS and DANE (they protect inbound mail; no major receiver requires them for outbound).

## 3. Operator console

### R-11 Console stack
- **Decision**: React 19 and Vite 8 (MIT), React Aria Components 1.22 (Apache-2.0) for accessible primitives, React Router 8 (declarative mode), TanStack Query 5, `openapi-fetch` for typed calls, React Hook Form with Zod 4 (`z.config({ jitless: true })` so no `eval` probe), `react-intl` (BSD-3-Clause; ICU MessageFormat like the Flutter ARB files), plain CSS files with custom properties and logical properties (RTL-ready), MapLibre GL JS 6 (BSD-3-Clause) for the coordinate picker.
- **Rationale** (R2, measured): a strict CSP and an axe run (WCAG 2.0/2.1 A and AA tags) produced zero violations in English and in Arabic RTL on a page with a table, dialog, select, form, map and image viewer. App chunk 225 kB gzipped; the map chunk 296 kB is lazy.
- **Rejected**: MUI X Data Grid Pro (paid tier), Radix (no table, calendar or date picker set), Lingui (needs Babel or SWC), i18next, Tailwind (fine, but plain CSS is simpler).
- **CSP** (production only): `default-src 'none'; script-src 'self'; style-src 'self' 'sha256-<hash of the one React Aria style element>'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; worker-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; object-src 'none'` plus a report endpoint. React Aria injects one `<style>` element that a static host cannot nonce, so its content hash is allowed; a Playwright CSP smoke test fails if the hash drifts. MapLibre needs `setWorkerUrl` with the Vite `?url` import. Caddy serves `.mjs` as `text/javascript`.
- **Language**: English at launch, every string localizable, `<html dir>` driven; other languages in Phase 4 (spec D11).

### R-12 Evidence viewer shows images only
- **Decision**: Uploaded images are re-encoded to WebP and PDFs are rasterised to page images; only those derived images are encrypted and stored. The console shows `<img src=blob:>`. No PDF engine runs in any browser (`pdfjs-dist` is not shipped).
- **Rationale** (R5, over R2's pdf.js plan): smaller browser attack surface (a pdf.js code-execution CVE existed in 2024); the originals are never served; Operators verify by phone call anyway.
- **Cost**: loss of original PDF fidelity and signatures. Documented in the evidence policy.

## 4. Evidence, privacy and audit

### R-13 Evidence storage and encryption
- **Decision**: Encrypted files on a dedicated directory owned by a separate Unix user, behind an `EvidenceStore{put,get,delete}` interface (so Garage, AGPL, could be adopted later). Per-file AES-256-GCM through `node:crypto` (one-shot; files are at most about 2 MB after re-encoding), a random 32-byte data key per file wrapped by a key-encryption key, additional authenticated data = file id, claim id and key id, blob header `magic | version | kek_id | nonce | ciphertext | tag`. The key-encryption keys, the audit pepper and the TOTP-secret key live in a SOPS (MPL-2.0) file encrypted to two founders' `age` (BSD-3-Clause) keys and the server's key. Key rotation re-wraps data keys only.
- **Honest limit**: decryption is on the server in Phase 1, so a live server compromise exposes the evidence that still exists. Keys held outside the server (decrypting in the browser with an Operator-group `age` key) is a documented Phase 1.5 option, not Phase 1: the server must re-encode plaintext at upload, and a compromised server could also serve malicious console code.
- **Access path**: no direct URLs. the Operator evidence route (`GET /v1/operator/cases/{caseId}/evidence/{evidenceId}`) checks authorization (reviewer, assigned to this open case, step-up within 5 minutes), writes `evidence.view_start` to the audit log inside a transaction (fail-closed: no audit row, no decryption), then streams. Committee contacts live in a separate table readable only by the assigned Operator while the case is open (FR-032), each view audited. Super-admins have no implicit read.
- **Store alternatives**: Garage (AGPL-3.0, no at-rest encryption of its own), SeaweedFS (Apache-2.0, several processes), MinIO (archived 2026-04-25, unmaintained: do not use).

### R-14 Upload pipeline
- **Decision**: limits 10 MB per file, 8 files and 40 MB per claim; magic-byte allow-list (JPEG, PNG, WebP, PDF; `file-type`, MIT); everything else rejected (archives, Office, SVG, HEIC, GIF). Images are re-encoded to WebP (maximum 3000 px, 40 megapixel input cap, metadata dropped); PDFs are rasterised with `pdftoppm` (at most 10 pages, 150 dpi, 20-second timeout) and then re-encoded. The tools run as separate executables (libvips `vips`, poppler `pdftoppm`) inside a sandbox with no network, memory and time limits; original filenames are discarded; disk names are random UUIDs.
- **Why not `sharp`**: it links LGPL libvips in-process, which principle 10 forbids outside a separately run server-side process (R2); it would also fail the planned npm license scan. The CLI tools are separate processes, which the constitution allows.
- **ClamAV** is rejected for this server (about 1.2 GiB for signatures alone). Recorded as an ASVS 5.4.3 deviation with compensating controls: allow-list, full re-encode, sandboxed parsers, original bytes never stored.

### R-15 Deletion and backups
- **Decision**: 90 days after the final decision a daily sweeper crypto-shreds (sets `wrapped_dek` to null), deletes the contact rows and notes, writes an `evidence.purged` audit entry, then unlinks the blob (key first, so a failed unlink still leaves unreadable data). An appeal sets a hold; a 30-day reminder to the super-admin prevents forgotten holds. Evidence blobs are never in off-server backups; database backups (which hold only wrapped keys) are kept 30 days at most. After any restore the sweeper reruns; cases whose blob is missing show "evidence missing, request re-upload".
- **FR-016.9 (identical evidence stays rejected)**: needs a fingerprint that outlives the evidence. Plan default: keep only an HMAC-SHA256 fingerprint of the sanitised images (pepper from SOPS) for 12 months after the rejection, and tell the admin. Owner decision and legal review needed (plan.md).

### R-16 Audit log
- **Decision**: `audit_log` is append-only. Row-level triggers on state tables write a row through a `SECURITY DEFINER` function in the same transaction (100% coverage for SC-008, including `psql` and migrations); the actor comes from `set_config('app.actor', ..., true)` inside each Kysely transaction. Semantic events (decision reasons, "Operator viewed evidence", break-glass approvals, logins) go through `audit_event(...)`. The app role has `SELECT` only; `UPDATE`, `DELETE`, `TRUNCATE` are revoked and a trigger raises on them. Each row carries `prev_hash` and `row_hash` (SHA-256 chain, serialised with an advisory lock); the head hash is anchored daily off-server. A nightly job verifies the chain.
- **Anonymisation**: rows hold a random `actor_ref`; the `actor_map` table (actor to account) is deleted when an account is deleted, so entries stay but become unlinkable (FR-024) without any `UPDATE`.
- **Measured** (R2 prototype, PostgreSQL 18): `UPDATE`, `DELETE`, `TRUNCATE` and `INSERT` as the app role all fail with "permission denied".
- **Read access**: admins read rows for their own Masjids only, without evidence events, committee-contact events or Operator names; Operators read all, and their reads are audited; Muazzins none; a data subject receives their own rows in an export.
- **Retention proposal (needs legal review)**: operational audit 24 months; evidence and contact-access events 12 months after the purge date; Masjid version history for the life of the listing; chain anchors indefinitely.

### R-17 Listener-side privacy (static read path)
- **Decision**: `data.` has no `log` directive at all, so no address and path pair is ever written. Caddy error logs are filtered (`remote_ip` masked, headers removed) and tested with a known address. Metrics are aggregate by host and status only (`metrics` with `per_host`); no per-cell label, no address label. Cell packs are padded with incompressible bytes to fixed transfer-size classes (4, 16, 64, 256 and 512 KB, ratio 4) so response size does not identify a cell; this hides sizes only from an observer who already sees the address, timing and nine requests, so it is kept modest (a 64 KB minimum would make a first download about 580 KB). No `fail2ban` on the pack host; journald volatile for the Caddy unit; no `LOG` firewall rules on 443.
- **Honest disclosure** (privacy notice and first-download consent): the server operator and the hosting provider can see a phone's IP address and that it connected; we do not log which area is downloaded; nobody can link a request to a Masjid; use a VPN if that matters. The consent screen offers "Download this area", "Download whole country" (reveals only a country) and "Not now".
- **Rate-limit keys** on public routes: HMAC of the address with a daily-rotating salt, in Valkey only, time to live at most 1 hour, never in PostgreSQL, logs or backups; a test asserts that. This reconciles "rate-limit suggestions" (FR-022) with "store no identifiers" (FR-003, FR-027).
- **Admin-side logs**: `auth_events` keeps the raw address 30 days (brute-force defence, legitimate interest), then truncates it (/24 or /48) for 12 months, then deletes it; application logs 14 days; Valkey counters at most 24 hours. Listener-facing hosts persist no address anywhere.
- **Suggestions and abuse reports**: an existing Masjid sends its id and correction text; a new Masjid sends the 5 km cell, the country and free-text name and address, and an Operator places the pin (plan default; owner decision, see plan.md). A proof-of-work challenge (self-hosted, Altcha, MIT, version UNVERIFIED) plus a honeypot guard the public POSTs.

## 5. Infrastructure, cost and operations

### R-18 Server and cost
- **Decision**: one VPS with 2 vCPU, 4 GB RAM and 40 GB disk, Docker Compose, no orchestration. Hetzner is not orderable now (cost-optimised plans show unavailable; status notice open since 2026-06-26; prices rose in June). Primary candidate: OVHcloud VPS-1 (2 vCPU, 4 GB, 40 GB NVMe) at EUR 3.81 (about US$4.28) per month on the 12-month price; the monthly-term price is UNVERIFIED. Fallback: Contabo Cloud VPS 4 (4 vCPU, 8 GB, 100 GB) at EUR 5.50 per month. Oracle Always Free is not advisable (freemium, idle reclaim). Provider purchase is gated on a day-0 port-25 and reverse-DNS test (R-10).
- **Cost** (US$ per month, EUR 1.1234): baseline VPS 4.28 + domain 1.00 (UNVERIFIED) + second backup copy on a team machine 0 = **5.28**; with VAT 6.14. Adding a Hetzner Storage Box (EUR 3.20) gives 8.87 before VAT and **10.41 with 19% VAT**, which breaks the US$10 ceiling. The all-in check therefore uses the team machine as the second copy; the Storage Box is optional only when VAT does not apply.
- **Alert thresholds**: warn above US$8.00 per month, breach action above US$9.50; any vendor price rise above 25% or a plan marked unavailable starts a fallback migration within 30 days.

### R-19 Compose profiles and the RAM rule
- **Decision**: three profiles with numeric rules. `core` always: Caddy, API, worker, PostgreSQL with PostGIS, Valkey, (Postfix and OpenDKIM on the host), node_exporter, restic timer, WireGuard. Estimated peak 1.7 GB. `observe` (Prometheus, Grafana) only if RAM is at least 4 GB and the 7-day p95 of available memory with `core` running is at least 1.2 GB; otherwise Prometheus runs on the team machine and scrapes over WireGuard. `full` (Loki, Alloy, postgres_exporter) only if RAM is at least 8 GB and available memory with `observe` is at least 2.5 GB. If swap-in exceeds 200 MB for 10 minutes or available memory drops below 300 MB twice in 24 hours, demote `full` to `observe` to `core` (a runbook step).
- **Uptime Kuma (MIT)** runs on a team member's always-on machine, not on the server (a monitor on the same box cannot report its death), with a push heartbeat from the backup job; a scheduled GitHub Actions probe is the last resort. Alerts go to the member's mailbox or a self-hosted ntfy (Apache-2.0).
- **Memory facts** (R2, measured on Node 26): API plus worker 170 to 210 MB idle, 400 to 500 MB if both peak; a hello-world Fastify idles at 69 MB.

### R-20 Capacity and the second-node trigger
- **Model** (R3): 50,000 listeners per day, three opens each; average about 337,000 requests and 4 GB per day (about 3.9 requests per second); worst day (every listener fetches nine 500 KB cells) about 225 GB; prayer-time herd about 120 opens per second in the first minute of a window, mostly 304 responses. A single vCPU serves these static files far above that rate (verified by the load test, not assumed).
- **Contract rules that keep it true**: schedule refresh at app open fetches only the manifest and the schedule layer; packs only when the manifest hash for a cell changes; client jitter of 0 to 120 seconds on prayer-time refresh; at most three parallel downloads; exponential back-off on 429 and 5xx.
- **Second node** (a static-only edge, rsync pull and DNS round-robin, not a database replica, about US$4): peak above 1,000 requests per second at a prayer window sustained, egress above 150 Mbit/s for 5 minutes, host CPU p95 above 60%, monthly egress above 5 TB, or manifest p95 above 300 ms. It adds cost beyond the ceiling, so it needs a budget decision.

### R-21 Caddy
- **Decision**: stock official image pinned by digest, no third-party modules. Pre-compressed `.br` and `.gz` sidecars (`file_server { precompressed br gzip }`, no per-request CPU). Cache classes follow the R-29 table (manifest `max-age=300, must-revalidate`; base `max-age=86400, stale-while-revalidate=604800`; overlay and schedule bundles `max-age=900`, all with ETag; pack paths are not content-addressed, so none is `immutable`); console HTML `no-cache`; hashed console assets immutable; API `no-store`. Keep old generations at least 30 days. HTTP/3 enabled (open UDP 443). TLS issuer pinned to Let's Encrypt only (Caddy's default ZeroSSL fallback has paid tiers). Admin endpoint and metrics bound to loopback or WireGuard. API rate limiting is done in Fastify, not Caddy (the Caddy rate-limit module is third-party and pre-1.0).
- **Header set** on every site: HSTS `max-age=63072000; includeSubDomains` (no `preload` until every subdomain is proven HTTPS-only), `nosniff`, `Referrer-Policy: no-referrer`, a deny-all `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy`, `-Server`.

### R-22 Backups and restore
- **Decision**: `pg_dump -Fc` plus `pg_dumpall --globals-only` every 6 hours (RPO 6 hours), transported and encrypted by restic (BSD-2-Clause) to a team-controlled second location. Retention: 14 daily plus 2 weekly dumps (at most 30 days, because dumps hold committee contact details and wrapped evidence keys, FR-032); no monthly copies; evidence blobs excluded. pgBackRest (point-in-time recovery) is overkill for a database under 1 GB. The second copy is a pull-model restic or `rest-server` repository on a team member's always-on machine over WireGuard, so a hacked server cannot delete history; the repository password and the `age` key are held by two operators and escrowed offline. Restore target: 2 hours 45 minutes, hard limit 4 hours (SC-006); the timed drill (R3 and R7) runs on a real second VPS that then becomes production.
- **Alternatives**: Hetzner Storage Box (optional, costs the margin), Garage or SeaweedFS (needs another host), free object-storage tiers (freemium SaaS: no).

### R-23 Infrastructure as code and host hardening
- **Decision**: `infra/bootstrap.sh` (the same content works as cloud-init user data), `infra/compose/docker-compose.yml` with profiles, `infra/caddy/Caddyfile`, SOPS-encrypted secrets, a Makefile (`make deploy` is `ssh` plus `sops -d | docker compose up -d`). No OpenTofu (only DNS would be managed) and no Ansible (GPL-3.0 dev tool, a second runtime for one host). The restore drill uses the same script.
- **Hardening**: SSH keys only, root login and passwords off, reachable via WireGuard or rate-limited; firewall default-deny; only Caddy publishes ports (the Docker-and-ufw bypass is handled in the `DOCKER-USER` chain); unattended security upgrades; read-only containers, non-root, `cap_drop: [ALL]`, `no-new-privileges`, memory limits from the RAM budget, image digests pinned; the Docker socket is never mounted into a container.

## 8. Directory data, packs, search and maps

### R-26 Seeding from OpenStreetMap
- **Decision**: Geofabrik country extracts are the primary source (daily refresh, ODbL, no stated download limits; be polite: conditional GET, at most one download per country per month). `osmium tags-filter` (GPL-3.0, separate build-time process, never linked) reduces a country to Muslim places of worship; `osm2pgsql` (GPL-2.0, flex output) loads a PostGIS staging schema; SQL refines. The planet file (95 GB) is a one-off on a build machine or in CI, never on the server. The Overpass API is for weekly deltas of pilot countries only (a world query returned HTTP 504; fair use is about 10,000 queries and 1 GB per day).
- **Filter**: keep (`amenity=place_of_worship` and `religion=muslim`) or (`building=mosque` with no religion tag, flagged `needs_review`); drop `disused:*`, `abandoned:*`, ruins, schools (madrasa) and cemeteries; `kind` is `mosque` or `musalla`. Live counts (2026-10-20): 341,358 objects with `religion=muslim`; 291,919 with `amenity=place_of_worship`; about 290,000 to 320,000 distinct Masjids worldwide.
- **Tag allowlist** (privacy and licence hygiene): `name`, `name:ar`, `name:en`, `name:ur`, the country-language name, `int_name`, `alt_name`, `official_name`, `old_name` (search only), `addr:*`, `denomination`, `place_of_worship`, `wikidata`. Dropped: `phone`, `contact:*`, `email`, `website`, `operator`, `note`, `fixme`, `source*` (personal data; contacts live in the overlay behind the API). `name:ar-Latn` has only 249 uses worldwide, so a Latin search key is generated with ICU Arabic-Latin transliteration. `denomination` has no madhhab values, so madhhab, method and variant come from the overlay.
- **Measured quality** (five countries): 12 to 54% of Masjids have no name, and Arabic names are rare outside Egypt; the UI needs an "unnamed mosque, 300 m" label.
- **Identity**: our own id `m` + 7 random base32 characters, assigned once, never derived from OSM ids; `masjid_osm_ref(osm_type, osm_id, masjid_id, first_seen, last_seen, status)`. Re-import: exact reference updates OSM fields unless an Operator override exists; a new object within 50 m with name similarity of at least 0.6 (or a node inside an existing Masjid's building outline) attaches as a new reference; a vanished object keeps claimed or verified Masjids (flagged to Operators) and hides unclaimed ones only after two consecutive imports, emitting a tombstone; Operator merges are kept as aliases and published in `redirects.json` (ids only, at least 12 months) so followed ids on phones remap.
- **Duplicates** go to an Operator queue, never auto-merged (FR-022): high = within 30 m and (shared normalised name, or a node inside a building outline, or one side unnamed); medium = within 150 m and `pg_trgm` similarity of at least 0.35. Cross-script pairs are compared after normalisation; direct Arabic-to-Latin similarity is near zero. `pg_trgm` behaviour on Arabic is UNVERIFIED: test on a UTF-8 database before relying on it.
- **Refresh**: monthly full re-import per enabled country, optional weekly delta for pilot countries; the replication timestamp is recorded per generation.
- **Curated list** (Two Holy Mosques and others): facts from the official source and Wikidata (CC0), `sources[]` recorded per entry (url, retrieved, licence); never copy proprietary map data or Wikipedia text. Where an OSM object exists the entry links to it and is then ODbL anyway.
- **Alternatives**: Overpass only (rate limits), osmosis (superseded), planetiler (tile builder, not an importer).

### R-27 ODbL: two layers, two files
- **Decision**: per 5 km cell, two files joined on our id on the phone: `base` (OSM-derived and curated facts: names, location, address, denomination, kind; ODbL; the Derivative Database) and `overlay` (status badge, admin madhhab, calculation method, Azaan variant, schedule revision; project terms; references base only by id). Contacts and photos are never in any pack; they stay behind the API.
- **Why**: the OpenStreetMap Foundation's guidelines treat extractable packs as a Derivative Database (not a Produced Work). A single mixed file would likely force the overlay open and would hand scrapers both layers under one header. Separate files make the licence boundary a directory, keep base ETags stable (monthly) while overlay changes daily, and let the open dump equal the base files byte for byte. Cost: one extra request per cell that has overlay data (the pilot has 0 to 3 of nine).
- **Rules that keep layers separable**: an Operator's edit of a name, location or address goes into the base layer as an override (published under ODbL and offered upstream to OSM); overlay madhhab is a separate field from OSM `denomination`; the phone's merged SQLite is a local cache and is never exported (no "export my Masjids" that mixes layers); listener-suggested new Masjids enter the base layer, so the submission terms grant ODbL-compatible rights and moderators reject copies from other databases.
- **Honest limit**: static files cannot technically stop bulk scraping of overlay files; "never exported in bulk" is a terms position backed by rate limits, not enforcement. The overlay is deliberately low-sensitivity.
- **Attribution**: persistent footer `© OpenStreetMap contributors` (linked to https://www.openstreetmap.org/copyright) on every screen that lists or details OSM-derived Masjids, in the console footer and in the map corner; the full text (names, locations and addresses contain information from OpenStreetMap, made available under the Open Database License) in About, the dump README, `LICENSES/NOTICE` and the `lic` field of every pack file. About-only is risky for result lists, so the footer stays.
- **Open dump** (satisfies the ODbL offer of a machine-readable copy): `directory-base-{gen}.ndjson.gz` with the same record schema as packs, `LICENSE-ODbL-1.0.txt`, `NOTICE.md`, `SHA256SUMS`; served from `/dumps/` and as GitHub Release assets; one per generation, last 12 kept. The importer and generator are open source under `tools/directory-pack/`.
- **Needs a human licensing review before launch** (10 questions in r4 section 1; summarised in plan.md): whether base plus overlay by id is a Collective Database in every jurisdiction served; whether the merged on-phone SQLite counts as public use; sufficiency of footer attribution; contributor terms for suggested Masjids; the overlay's "no bulk redistribution" terms against principle 10's redistribution wording; vector map tiles as a Produced Work; imagery sources for Operator-edited coordinates; mixing Wikidata ids; and whether the SQLite build hook's download from GitHub needs a register entry.

### R-28 Cells, near me and parts
- **Decision**: geohash precision 5 (25 bits, 0.043945 degrees; 4.89 × 4.86 km at the equator, 4.01 km wide at 35 degrees, 3.46 km at 45, 2.45 km at 60). Precision 6 must never be requested. "Near me" fetches the fixed 3×3 block around the phone's cell, computed on the phone from its own location. A 3×3 block fully covers a radius only up to one cell width (4.9 km at the equator, 3.5 km at 45 degrees, 2.4 km at 60 degrees): the UI states the real radius ("within 3 km") and offers "widen" (the next ring, after a confirmation).
- **What the server learns**: nine adjacent cell ids from one address within a second, so the centre cell (about 24 km²) and that it is a near-me search; over time, the cells a device revalidates. It never learns a point or a Masjid.
- **Listener choices on the consent screen** (location read on the phone only): *Near me* (3×3 cells), *Area* (the precision-4 index `g4/{gh4}` and its non-empty children: the server learns only a 39 × 19 km box), *Whole country* (downloads only the country summary of major Masjids; reveals only a country) and *Manual* (country then city from Phase 0's bundled `cities.db`, no location used). Request order is randomised and jittered 100 to 800 ms; background refresh only for cells the user already holds, never new ones.
- **Parts** (resolves the FR-033 conflict): an oversized file is split into parts by `hash(id) mod N`, so a part carries no spatial meaning and nothing finer than the cell exists as a request target. `N = ceil(uncompressed bytes / 400 KB)`; the 500 KB limit applies to **uncompressed** bytes (deterministic whatever the `Accept-Encoding`). Part 1 is `{cell}.json` (also the unsplit case), later parts are `{cell}.p{n}.json`. Every part header carries `cell`, `part`, `parts`, `cv` (content hash of the whole set) and `gen`. The client reads part 1, fetches parts 2..N in parallel, checks that `cv` matches and commits all parts in one SQLite transaction or none; on a mismatch during a publish it retries (up to three times). The publisher writes parts 2..N before part 1 and flips a whole-generation symlink. Measured: the densest OSM cell today (Semarang, 445 Masjids) is 44 KB raw and 8 KB with brotli, so base parts will almost never trigger; they exist for growth and for schedule bundles.
- **Version detection**: the client keeps `{etag, cv, gen, fetched_at}` per cell and sends `If-None-Match`. The generator must not rewrite unchanged files or touch their modification time (Caddy builds its ETag from mtime and size, tested on Caddy 2.11.7, including `.br` and `.gz` sidecars, 304 and 206). Cheap check first: `GET /v1/manifest.json` at most every 12 hours; if `gen` and `overlay.gen` are unchanged the client skips every revalidation.
- **City and region browsing**: reuse Phase 0's bundled `cities.db` (country, city, in four languages) to find a city's centre cell; no server `places` index.

### R-29 Pack format and sizes
- **Decision**: gzip and brotli JSON with short keys, additive-key evolution and a major `v` in each header, about 26 bytes per Masjid after brotli. After compression all candidate formats (columnar JSON, MessagePack, Protobuf, FlatBuffers) are within about 15%; JSON needs no dependency, can be inspected with `curl` and is the dump format. Parsing 0.5 MB of JSON is trivial; SQLite inserts dominate (low-end Android timing is UNVERIFIED: benchmark in Phase 1).
- **Storage** (all variants kept): pilot of three countries about 135 MB of disk, five countries about 360 MB, world about 700 MB (block rounding dominates). Traffic check for SC-005: 50,000 listeners per day × (manifest + 9 cells ≈ 25 KB) ≈ 1.3 GB per day, about 7 requests per second.
- **Paths and cache headers** (`/v1` is the schema major, all on `data.<domain>`):

| Path | Cache-Control | Notes |
|---|---|---|
| `/v1/manifest.json` | `public, max-age=300, must-revalidate` + ETag | global, not location-specific; carries `gen`, `overlay.gen`, `min_app`, licence, stale rules |
| `/v1/base/{gh5}[.p{n}].json` | `public, max-age=86400, stale-while-revalidate=604800` + ETag | ODbL layer; 404 for empty cells (`max-age=3600`) |
| `/v1/overlay/index.json`, `/v1/overlay/{gh5}[.p{n}].json` | `public, max-age=900` + ETag | project terms; the index lists cells with overlay data |
| `/v1/sched/{gh4}[.p{n}].json` | `public, max-age=900` + ETag | schedule rule bundle per precision-4 area |
| `/v1/country/{ISO2}.json`, `/v1/g4/{gh4}.json`, `/v1/redirects.json`, `/dumps/*` | `public, max-age=86400` | the country file holds only major Masjids (name, location, id) |

All: `Vary: Accept-Encoding`, no cookies, `Referrer-Policy: no-referrer`; packs padded to size classes (R-17). Staleness: base older than 90 days shows a banner; a schedule bundle fetched more than 30 days ago means calculated times (US2 AC5); `min_app` above the app version shows "update app". The minimum-supported-app-version "endpoint" is therefore a field of the static manifest.
- **Schedule bundles per precision-4 area** (about 39 × 19 km): a request names an area, never a cell and never a Masjid. The bundle holds an id-only stub for every Masjid in the area and rules for the Verified ones, so file size does not reveal which Masjid a phone follows. Each rules record carries the IANA zone, a revision and the rule list (`masjid-schedule/1`, defined in contracts/schedule-rules.md). A residual not solved here: Firebase push topics per Masjid (a later phase) would reveal the Masjid to Google; flagged to the push design.
- **Alternatives**: one merged file per cell (rejected: licence), per-Masjid schedule files (rejected: reveals the Masjid), Protobuf (best evolution, extra tooling, no real size gain).

### R-30 Local search on the phone
- **Decision**: FTS5 is available in the app's `sqlite3` 3.7.1 build (MIT; compile options include `SQLITE_ENABLE_FTS5`, `RTREE`, `MATH_FUNCTIONS`; confirmed from the package's own documentation and a desktop run; an Android and iOS CI test must create an FTS5 table with the trigram tokenizer). `sqlite3_flutter_libs` is an obsolete empty package: do not add it. A separate rebuildable `directory.db` (like Phase 0's `cities.db`), user data stays in drift `app.db` (schema 1 to 2).
- **Arabic**: `unicode61 remove_diacritics 2` folds Latin accents but not Arabic tashkeel (query `مسجد` did not match `مَسْجِد`); text must be normalised in code on both the indexed text and the query. The Dart normaliser (the same function runs in the generator for the `sx` Latin key, with shared vectors, reusing Phase 0's `name_normalizer.dart`): NFKC; remove tashkeel U+064B to U+065F and U+0670 and tatweel; alef variants to alef; ى to ي; ة to ه; ؤ to و; ئ to ي; Persian and Urdu letter forms to Arabic forms; Arabic-Indic digits to ASCII; Latin lowercased with marks and apostrophes removed; index with and without the leading `ال` or `al-`; mosque words (masjid, mosque, masjed, mesjid, camii, cami, jami, jama, musalla) mapped to one dropped synonym token.
- **Index**: tables `masjid`, `cell_state(layer, cell, etag, cv, gen, parts, fetched_at)`, FTS5 `masjid_fts(s)` with `prefix='2 3'` for type-ahead and an optional trigram table for Latin typo tolerance (about 3× bigger, fine below about 50,000 rows). Ingest per download is one transaction. Near-me sorting: bounding box on latitude and longitude, `ORDER BY dlat² + (dlon·cos lat0)²` in SQL, exact haversine in Dart for the label; the R*Tree module exists but is unnecessary below about 50,000 rows. Text search offline sends nothing; online search for undownloaded places (if built) sends only the typed text by POST.

### R-31 Maps
- **Decision**: the Flutter app has **no map in Phase 1** (lists with distance only): a map would send tile requests with z/x/y at street zoom, which is a location finer than 5 km (violating FR-011 and SC-004) unless tiles were bundled offline (hundreds of MB), and it would add native MapLibre binaries and attribution UI for no requirement. The console's coordinate picker uses **self-hosted PMTiles** (Protomaps basemap build; go-pmtiles BSD-3-Clause, `pmtiles` JS 4.5.0 BSD-3, `@protomaps/basemaps` 5.7.2 BSD-3, MapLibre GL JS 6.15.0 BSD-3-Clause) served by Caddy with HTTP range requests (tested: 206) from `console.<domain>/tiles/`. Fallback: list plus coordinate entry (FR-029), which also ships if the server cannot hold the tiles.
- **Size**: z0 to 13 nationally plus z14 to 15 clipped to city boxes, about 1 to 2 GB for three pilot countries (z0 to 14 whole country: Indonesia 911 MB, Pakistan 669 MB, Egypt 166 MB); extracted on a laptop or in CI, refreshed quarterly, excluded from backups. Load: a handful of admins, under 1 request per second, tens of KB each: negligible CPU and RAM; the cost is disk.
- **Fonts and glyphs**: copied from `protomaps/basemaps-assets` (Noto Sans under SIL OFL; sprites from MIT sources) to our own host. Arabic labels may need the `@mapbox/mapbox-gl-rtl-text` plugin (BSD-2-Clause); whether MapLibre 6 still needs it is UNVERIFIED: test with Arabic names. Attribution control shows `© OpenStreetMap contributors`.
- **Rejected**: OpenFreeMap (a hosted third party with "a paid Pro plan may come later" touches principle 10; usable only as a documented emergency fallback after a constitution decision), the public OSM tile servers (policy forbids bulk and offline use, no SLA), any Google or Mapbox service.
- **Later** (Phase 3 or after): offline PMTiles regions as explicit downloads with `maplibre` 0.3.6 or `maplibre_gl` 0.27.1 (both BSD-3-Clause; PMTiles support UNVERIFIED).
